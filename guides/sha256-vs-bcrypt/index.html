SHA-256 vs Bcrypt: When to Use Each for Password Storage

SHA-256 and bcrypt are both hash functions. One is fast, general-purpose, and completely unsuitable for passwords. The other is deliberately slow, salted, and built for exactly one job — protecting user credentials. Mixing them up is one of the most common security mistakes in production code.

By Emiliano · Published November 16, 2026 · 10 min read

What is a password hash?

A password hash is a one-way mathematical transformation. You feed it a password, and it returns a fixed-length string. You cannot reverse the operation — you cannot "decrypt" a hash to recover the original password.

When a user signs up, you store the hash. When they log in, you hash what they typed and compare. If the hashes match, the password is correct. This means a database breach does not expose plaintext passwords — attackers get hashes, which they must crack.

The security of this model depends entirely on how expensive it is to compute each hash. Fast hashes are cheap for you and cheap for attackers. Slow hashes are cheap for you and expensive for attackers. That is the entire design rationale behind bcrypt — and the reason SHA-256 should never be used for passwords.

What is SHA-256?

SHA-256 is a cryptographic hash function published by the NSA and standardized by NIST in FIPS 180-2 (2001) and later refined in FIPS 180-4 (2015). It belongs to the SHA-2 family, alongside SHA-224, SHA-384, and SHA-512.

SHA-256 always produces a 256-bit (32-byte) output, regardless of input size. It is designed for speed and collision resistance — two properties that make it ideal for content integrity, digital signatures, and password-free cryptographic protocols.

SHA-256 is embedded in TLS 1.3, Bitcoin proof-of-work, Git commit hashing, and JWT signing via HS256. It is everywhere because it is fast, well-studied, and mathematically sound. Those same properties are exactly why it fails as a password hasher.

Key point: SHA-256 was never designed to be slow. Its speed is a feature for content verification and a catastrophic flaw for password storage.

How fast is SHA-256, really?

A modern CPU core computes roughly 1.5 GB per second of SHA-256 throughput. On a consumer GPU like the RTX 4090, that becomes approximately 20 billion hashes per second for simple password-length inputs. A $2,000 GPU can try every 8-character password in a typical user database in under a minute.

What is Bcrypt?

Bcrypt was designed by Niels Provos and David Mazières at USENIX 1999 specifically to make password cracking expensive. The paper, "A Future-Adaptable Password Scheme", introduced a "cost factor" that lets the algorithm be deliberately tuned to take longer as hardware gets faster.

Three properties define bcrypt:

  • Deliberate slowness. A cost factor of 12 means 212 = 4,096 iterations of an expensive key derivation. Each hash takes roughly 250ms on modern hardware.
  • Automatic salting. Bcrypt generates a random 16-byte salt for every hash and stores it inside the output string. Two identical passwords produce two completely different hashes.
  • Adaptive difficulty. When hardware gets faster, you raise the cost factor. The hash format supports this without changing your code.

What does a bcrypt hash look like?

$2y$12$R9h/cIPz0gi.URNNX3kh2OPST9/PgBkqquzi.Ss7KIUgO2t0jWMUW

The structure breaks down like this:

  • $2y$ — algorithm version (2y is the current standard)
  • 12 — cost factor (212 = 4,096 iterations)
  • R9h/cIPz0gi.URNNX3kh2O — 22-character salt (Base64-encoded 16 bytes)
  • PST9/PgBkqquzi.Ss7KIUgO2t0jWMUW — 31-character hash output

Everything the verifier needs is stored in the string itself. You never manage salts manually — bcrypt handles it.

Why is SHA-256 unsafe for passwords?

Three overlapping reasons:

  1. It is too fast. A GPU computes 20 billion SHA-256 hashes per second. With a rainbow table of common passwords, an attacker finds the plaintext of most users in minutes.
  2. It has no built-in salt. Unsalted SHA-256 hashes of the same password are identical across users. An attacker who cracks one hash cracks them all.
  3. It cannot be tuned. As hardware improves, SHA-256 gets faster for attackers. There is no way to make it slower for everyone.

The RockYou2024 leak exposed approximately 9.9 billion plaintext passwords. Any site that stored those passwords as unsalted SHA-256 hashes has effectively published its users' credentials. The hashes offer almost no protection against an attacker with a GPU and a leaked dictionary.

Common mistake: Some developers believe that using SHA-256 with a salt (e.g., sha256(salt + password)) makes it safe. It does not. Salted SHA-256 stops rainbow tables but still falls to brute-force cracking in seconds because the underlying hash is still billions of times too fast.

When should you use SHA-256?

SHA-256 is the correct choice whenever you need a fast, deterministic integrity check — not password protection. The common legitimate use cases are:

  • File integrity verification. Checking that a download matches a published hash, or verifying that a Git commit has not been tampered with.
  • HMAC signatures. Verifying message authenticity where the input is high-entropy and the risk is tampering, not brute-force. This is the mechanism behind JWT HS256.
  • Content addressing. Bitcoin, IPFS, and Git all use SHA-256 to identify content by its hash.
  • Password-derived keys in KDF chains. When SHA-256 is used inside PBKDF2 with high iteration counts (600,000+ per OWASP), it is acceptable — but at that point you are effectively using SHA-256 as a primitive inside a slow KDF, not as a password hasher directly.

What about JWT signatures?

You may have seen JWTs signed with HS256 (HMAC-SHA256). This is safe because the JWT secret is a long random string, not a low-entropy password. An attacker cannot brute-force a 256-bit random secret. To inspect a JWT safely, use our JWT decoder — it runs entirely in your browser.

When should you use Bcrypt?

Bcrypt is the correct choice for password storage, and only that. If you are storing user credentials in a database — signup, login, password reset — bcrypt is the tool.

  • User account passwords. Any interactive login where users type a password.
  • API keys that users create themselves. If the "key" is human-chosen, treat it like a password.
  • Password-protected exports or backups. Wherever you would otherwise be tempted to use SHA-256 on something human-memorable, use bcrypt instead.

What cost factor should you use?

The cost factor is a power of 2. Cost 12 = 4,096 iterations. Every increment doubles the time to compute one hash, both for you and for an attacker.

Use cost factor 12 as your default. It hits the sweet spot: logins still feel instant (250ms is imperceptible to a user), but an attacker with a GPU must run 250,000x slower than they would against SHA-256.

Why 250ms is safe: Logins happen once per user per session. A 250ms delay is invisible. But an attacker hashing a stolen database must run that 250ms for every guess — that is the difference between cracking 1 million passwords in a minute (SHA-256) and 4,000 passwords per second (bcrypt cost 12).

Common mistakes developers make

  1. Using SHA-256 for passwords. The single most common security bug in code review.
  2. Using bcrypt but with a low cost factor. Cost 4 (16 iterations) offers almost no protection. Always use cost 12.
  3. Using MD5 or SHA-1 for passwords. Both are cryptographically broken and even faster than SHA-256. Never use them for security purposes.
  4. Manually salting SHA-256. Salted SHA-256 is still far too fast. Salting does not fix the speed problem.
  5. Storing passwords in a reversible format. Encryption is not hashing. If the key leaks, every password leaks instantly.
  6. Ignoring the 72-byte bcrypt limit. Passwords longer than 72 bytes are silently truncated. For very long passphrases, use Argon2id instead.

What are the modern alternatives to bcrypt?

Bcrypt is still excellent, but three newer algorithms address specific limitations:

  • Argon2id. Winner of the 2015 Password Hashing Competition. Recommended by OWASP as the first choice in 2026. Memory-hard — requires configurable RAM in addition to time. No 72-byte limit.
  • scrypt. Memory-hard like Argon2. Simpler to implement, older, well-studied. A reasonable choice when Argon2 is unavailable.
  • PBKDF2 with SHA-256. Acceptable when configured with 600,000+ iterations (OWASP 2026 recommendation). Only worth choosing for legacy compatibility — it is not memory-hard.

For a new project in 2026, the priority is: Argon2id > bcrypt (cost 12) > scrypt > PBKDF2. Bcrypt remains safe as long as your cost factor is at least 12.

Frequently asked questions

Can I use SHA-256 to store passwords?

No. SHA-256 is too fast — a modern GPU can compute roughly 20 billion SHA-256 hashes per second. That makes brute-forcing stolen password hashes trivially cheap. Use bcrypt, scrypt, or Argon2 instead, which are designed to be slow.

What bcrypt cost factor should I use in 2026?

Use cost factor 12. It takes roughly 250ms per hash on modern hardware, fast enough for logins but slow enough to make offline cracking expensive. Never go below 10.

Does bcrypt include a salt automatically?

Yes. Bcrypt generates a random 16-byte salt for every hash and stores it inside the output string. You never manage salts manually. SHA-256, by contrast, has no built-in salt.

Is SHA-256 still secure for JWT signatures?

Yes. HS256 (HMAC-SHA256) is a standard JWT signing algorithm and is secure for token integrity. The key insight is that SHA-256 is unsafe for password storage but safe for integrity verification where the input is not a low-entropy secret.

What is the bcrypt 72-byte password limit?

Bcrypt only processes the first 72 bytes of input. Passwords longer than 72 bytes are silently truncated. If you need unlimited password length, use Argon2id or scrypt instead.

The bottom line

SHA-256 and bcrypt are both cryptographic hash functions, but they were designed for opposite purposes. SHA-256 is optimized for speed and integrity — it is the correct tool for file checksums, HMAC signatures, and content addressing, but the worst possible choice for password storage.

Bcrypt is optimized for exactly one job: making passwords expensive to crack. Use it with cost factor 12, and it will protect your users even if your database leaks tomorrow.

If you are auditing code and see sha256(password), that is a bug. If you see sha256(password + salt), that is still a bug. The correct pattern is bcrypt.hash(password, 12) — and nothing else.
