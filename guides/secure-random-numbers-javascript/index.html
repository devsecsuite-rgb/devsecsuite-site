How to Generate Secure Random Numbers in JavaScript (2026)

Every developer has typed Math.random() to generate a token, an ID, or a password. It is one of the most common security mistakes in JavaScript. This guide explains why, what to use instead, and how to use the right API without introducing a subtler bug — modulo bias.

By Emiliano · Published November 19, 2026 · 10 min read

Why Math.random() is not secure

Math.random() returns a floating-point number between 0 (inclusive) and 1 (exclusive). It is fast, simple, and completely wrong for anything involving security.

Under the hood, Math.random() is typically implemented as xorshift128+ or V8's own PRNG, seeded from a combination of the current time, the process ID, and some system entropy. The result is deterministic: given the same seed, the sequence of outputs is identical.

This means an attacker who can observe a handful of Math.random() outputs can reconstruct the internal state and predict all future outputs with high accuracy. In 2015, researchers at Brave demonstrated they could recover V8's PRNG state in under 30 seconds from a single browser session. Three years later, a bug bounty report showed that a well-known password manager was using Math.random() to seed its password generation.

Rule of thumb: if the value is used for security, and you typed Math.random(), you have a bug. Passwords, tokens, session IDs, CSRF values, OTPs, and salts all require a cryptographically secure source.

When Math.random() is fine

Not every use of randomness is security-relevant. You can safely use Math.random() for:

  • Visual effects — random particle positions, confetti, glitch animations.
  • Placeholder content — lorem ipsum variants, sample data in non-security demos.
  • Non-security game mechanics — dice rolls in a single-player local game, random card shuffle for a solitaire (not for online poker).
  • Performance-based sampling — picking 1% of requests to profile. The value is observable but not exploitable.

The dividing line is simple: if an attacker benefits from predicting the output, you need a cryptographically secure source. If not, Math.random() is fine and fast.

Enter crypto.getRandomValues()

The Web Crypto API exposes crypto.getRandomValues(), which fills a TypedArray with random bytes drawn from the operating system's cryptographically secure pseudorandom number generator (CSPRNG). On macOS and Linux this is /dev/urandom. On Windows it is CryptGenRandom or BCryptGenRandom.

The basic API — a 5-line example

// Fill a 16-byte buffer with cryptographically secure random data
const bytes = new Uint8Array(16);
crypto.getRandomValues(bytes);

// Convert to hex string: "a3f2c1..."
const hex = Array.from(bytes).map(b => b.toString(16).padStart(2, '0')).join('');
console.log(hex); // 32-character hex string with 128 bits of entropy

That is the correct way to generate a secure token in the browser. Two things to note:

  • The buffer is exactly 16 bytes. Use 32 bytes (256 bits) for API keys and long-lived tokens.
  • The output is a hex string. Encode as Base64 for shorter strings, or keep hex for readability.

The subtle bug: modulo bias

Here is the most common mistake developers make when trying to do the right thing:

// WRONG — biased
function randomChar(pool) {
  const bytes = new Uint8Array(1);
  crypto.getRandomValues(bytes);
  return pool[bytes[0] % pool.length];
}

This looks correct. It uses crypto.getRandomValues(), the secure API. But it introduces modulo bias.

Here is the problem. bytes[0] is a random number between 0 and 255. pool.length might be 62 (a-z, A-Z, 0-9). 256 % 62 = 8, which means the first 8 characters of the pool (a–h) get 9 possible values each (from 0, 62, 124, 186...) while the remaining 54 characters get 8 possible values each. The first 8 characters are 12.5% more likely to appear. Over 16 characters, that is a measurable bias.

For passwords, this means real passwords are slightly less random than the entropy calculation claims. For a 20-character password, the effective entropy drops by roughly 3–4 bits — not catastrophic, but preventable.

The fix: rejection sampling

The fix is to discard any random value that would cause bias, and only accept values that are evenly distributed across the pool. This is called rejection sampling:

function randomChar(pool) {
  const MAX = 256;
  const limit = Math.floor(MAX / pool.length) * pool.length; // e.g. 248 for a 62-char pool
  const bytes = new Uint8Array(1);
  do {
    crypto.getRandomValues(bytes);
  } while (bytes[0] >= limit);  // discard values 248–255
  return pool[bytes[0] % pool.length];
}

Now every character has exactly 4 possible random values (248 / 62 = 4), so the distribution is uniform. Rejection happens for 256 - 248 = 8 values out of 256 — about 3% of calls — which is negligible performance cost.

Generating a secure password — the complete function

function generatePassword(length, pool) {
  const MAX = 256;
  const limit = Math.floor(MAX / pool.length) * pool.length;
  const bytes = new Uint8Array(length * 2); // over-allocate for rejections
  let password = '';
  let idx = 0;

  while (password.length < length) {
    if (idx >= bytes.length) {
      crypto.getRandomValues(bytes);
      idx = 0;
    }
    const byte = bytes[idx++];
    if (byte < limit) {
      password += pool[byte % pool.length];
    }
  }
  return password;
}

const pool = 'ABCDEFGHIJKLMNOPQRSTUVWXYZabcdefghijklmnopqrstuvwxyz0123456789';
console.log(generatePassword(20, pool));

This function is safe to ship. It uses crypto.getRandomValues(), handles modulo bias via rejection sampling, and is fast enough that you would never notice the rejections.

Node.js equivalent

If you need the same logic on the server:

const crypto = require('crypto');

const bytes = crypto.randomBytes(32); // 256 bits
const token = bytes.toString('base64url');
console.log(token); // Base64URL-encoded 32-byte token

crypto.randomBytes() is the Node.js equivalent of crypto.getRandomValues() — both draw from the OS CSPRNG. In Node 15+ you can also use crypto.webcrypto.getRandomValues() for portability across browser and server code.

How much randomness do you actually need?

Entropy is measured in bits. Each additional bit doubles the search space an attacker must cover. Here are reasonable minimums in 2026:

API key160256 (32 bytes)
Password (generated)80128 (16 bytes)
Salt for password hashing128128 (16 bytes)
Password reset token128256 (32 bytes)

Those numbers are deliberately conservative. An 80-bit password provides enough resistance against offline brute-force for decades; 128 bits is fully future-proof. For tokens and IDs, use 256 bits — the extra cost is zero.

The 5 mistakes people make with crypto.getRandomValues()

  1. Using a 1-byte buffer for passwords. One byte = 8 bits of entropy per character. You need to accumulate bytes across the password, not call the API once per character.
  2. Modulo bias. Covered above — the most common mistake.
  3. Using Math.random() to seed crypto.getRandomValues(). Pointless. crypto.getRandomValues() does not accept a seed and does not need one.
  4. Reusing the same buffer without refilling. Each call to crypto.getRandomValues() overwrites the buffer. Reusing an old buffer means reusing old entropy.
  5. Converting bytes to a string with String.fromCharCode(). That mangles non-ASCII bytes. Use hex or Base64 encoding instead.

What about crypto.randomUUID()?

crypto.randomUUID() is a shorthand for generating UUIDv4 identifiers — 122 bits of entropy, format guaranteed by spec. It is safe for session IDs, correlation IDs, unique keys, and non-security-critical identifiers.

It is not safe for password generation because the format is publicly known — an attacker knows the dashes and the fixed version nibble, reducing effective entropy slightly and making dictionary-style attacks against generated passwords easier. For passwords, use crypto.getRandomValues() directly.

Frequently asked questions

Is Math.random() secure enough for passwords or tokens?

No. Math.random() is a pseudo-random number generator seeded by the time and other predictable values. Its state can be reconstructed from a handful of outputs, making it trivially predictable. It must never be used for passwords, tokens, session IDs, CSRF tokens, or any security-sensitive value. Use crypto.getRandomValues() instead.

What is crypto.getRandomValues() and how is it different from Math.random()?

crypto.getRandomValues() is part of the Web Crypto API and draws from the operating system's cryptographically secure pseudorandom number generator (CSPRNG). On macOS and Linux this is /dev/urandom; on Windows it is CryptGenRandom. Unlike Math.random(), the output cannot be predicted from previous outputs, even with full knowledge of the algorithm.

What is modulo bias and why does it matter?

Modulo bias happens when you take a random integer from a larger range and use modulo to fit it into a smaller range. Some values get more outcomes than others, making them slightly more likely. The fix is rejection sampling: discard random values that fall in the non-uniform remainder, and only keep values from the divisible portion of the range.

How many random bytes should I use for a password?

For passwords in 2026, use at least 16 random bytes (128 bits) generated from crypto.getRandomValues(), then Base64 or hex encode them. That produces a 22-character Base64 string or a 32-character hex string, both with over 100 bits of entropy — enough to resist offline brute-force attacks for decades.

Is crypto.getRandomValues() available in Node.js?

Node.js exposes crypto.getRandomValues() via the webcrypto module in Node 15+, or directly in Node 19+. For older versions, use crypto.randomBytes(), which is the equivalent server-side API. Both draw from the OS CSPRNG and are safe for security use.

Can I use crypto.randomUUID() for secure identifiers?

Yes. crypto.randomUUID() produces a UUIDv4 identifier with 122 bits of entropy, generated from the browser CSPRNG. It is safe for session IDs, correlation IDs, and unique keys. It is not safe for password generation because it exposes its own format — use crypto.getRandomValues() for those.

The bottom line

Math.random() is fast and predictable. crypto.getRandomValues() is slower and secure. Use the first for animations, the second for anything else.

When you generate the random bytes, avoid modulo bias by using rejection sampling — it costs 3% of iterations and eliminates the subtle weakness. And when you generate passwords, use at least 16 bytes, not the 1–2 bytes many online examples use.

If you are writing code that generates tokens or passwords, and you have not manually verified that your code uses a CSPRNG, assume it does not. That assumption has caught more production bugs than any other I have seen.
